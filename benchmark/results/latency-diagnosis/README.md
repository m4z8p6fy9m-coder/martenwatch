# Latency investigation (local, synthetic)

The earlier benchmark captured a 495 ms p99 over 360 workflows, but did not measure separate request phases. `npm run benchmark:diagnose` instruments create and simulate separately, with 20 warmup and 150 measured sequential workflows against the current local SQLite implementation. Raw measurements are in `results.json` and `samples.csv` beside this file.

In the captured follow-up, p50 was 50.11 ms, p95 65.88 ms and p99 81.91 ms. The slowest workflow took 110.51 ms, of which 101.45 ms was in the simulation request; the whole workflow used approximately 16 ms process CPU. This narrows the observed delay to that request and suggests wall time outside measured process CPU, but does not distinguish filesystem durability, OS scheduling, background activity, garbage collection, or other causes. No network or remote provider is involved. The original 495 ms outlier did not recur in this small run, so its cause is unproven. More repeated runs on a quiet system with OS-level disk, scheduling and garbage-collection tracing are needed. Process CPU includes driver and server and its Windows precision is coarse; subtracting it from wall time is not a measurement of disk latency. These local samples do not establish production performance.
