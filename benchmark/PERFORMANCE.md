# Local performance experiment: protocol and interpretation

Run `npm ci` on Node 24, then `npm run benchmark:performance`. It overwrites `benchmark/results/local-sanitized/` with `workflows.csv` (one measured workflow per row), `results.json` (environment, code hashes, run-level CPU/RSS/timing and raw recovery trials), and `REPORT.md`. No hosted service or model is called. The runner creates and deletes its own temporary SQLite databases.

## Design

The load is fixed: 20 warmup and 120 measured sequential synthetic workflows per process, three fresh processes per implementation (360 measured workflows each). Each workflow submits one valid below-threshold invoice and one simulated execution via in-process Fastify injection with local SQLite persistence. Both modes receive the same values. Mode order alternates by run. Nearest-rank p50/p95/p99 combine all 360 samples; throughput is the sum of successful and failed workflows divided by their total measured wall time. Error rate is the fraction whose create status is not 201 or simulation status is not 200. The raw rows include both response status codes. These are workflow timings, not HTTP request or real network latency.

The minimal baseline is an intentionally simple Fastify/SQLite implementation with a persisted invoice and simulated effect. It does not implement policy, human approval, auth, event audit, tracing, crash recovery or the same response bodies. ActionLedger adds those features and differs in implementation. The comparison is end-to-end implementation cost, not an isolated measurement of just a security decision. Both have sequential concurrency 1; results do not predict multi-user, remote database, cloud, model or real-payment performance. All measured requests are legitimate; this performance experiment does not measure attack effectiveness, false positives, or reliability under mixed attacks. See the separate security and reliability labs.

CPU time is the delta of Node process user + system CPU during measurement, including the in-process workload driver, not whole-machine utilization. Per-workflow CPU divides summed CPU time by workflow count. Peak RSS is the largest process RSS sampled after workflows, including runtime and warmup; it may miss transient peaks and is not exclusively application memory. Run-level values are in `results.json`. There is no system load isolation, disk cache control, fixed CPU frequency, confidence interval, statistical significance test, or true independent repeated-machine sample. Disk scheduling and background activity can dominate tail observations; do not infer general performance differences from one capture.

## Recovery measurement

Five separate trials queue a local idempotent simulated action, start a worker process, wait until it claims the job, send a hard termination, wait for its exit, and construct an ActionLedger app in the benchmark process. Timing starts before the kill signal and stops after app construction and synchronous startup recovery. Each trial verifies one local simulated effect and one completed job; raw durations and counts are in `results.json`. This includes worker termination overhead but excludes a newly spawned server process, external-provider reconciliation, and network recovery. The baseline has no recovery, so there is no baseline recovery time. Five observations cannot support stable p95 or p99 estimates. Unknown external-provider outcomes are covered by the reliability tests, not this performance measurement.

## Provenance and privacy

The runner records OS family and release, CPU model and logical cores, total RAM, Node version, run timestamp, Git commit and dirty state if a repository is available, and SHA-256 hashes of listed source files and lockfile. This directory was not a Git checkout during the captured run, so commit and dirty state are null; no commit should be invented. Hashes identify the listed files, not all dependencies, OS configuration or the complete working tree. Re-run from a committed clean checkout to capture a meaningful commit. Machine results may differ.

The output does not intentionally collect usernames, hostnames, IP addresses, school names, account data, invoice text, environment variables, filesystem paths or Git remotes. Hardware model, OS version and timestamp are still machine metadata and can be identifying in some contexts. Review these artifacts and the entire repository and Git history before any upload. These files are local and have not been published online.

The original captured report predates the first Git commit. Git normalized line endings for three benchmark scripts, so their byte hashes in that historical report do not match a fresh checkout, even when their text is unchanged. Do not treat that capture as reproducible from the commit bit-for-bit. A new benchmark run from a clean checkout records the current commit and fresh hashes; preserve its output separately when comparing results.
