# OpenAI Agents SDK integration: offline safety experiment

The SDK tool passes through `api/tool-gateway.mjs`, a local allowlisted boundary with strict arguments and an identity supplied by trusted application code. The backend still enforces authorization and invoice approval when test identity mode is enabled. A separate MCP server factory in `api/mcp-server.mjs` exposes the same gateway as a structured tool using the official MCP SDK. Run `node --test tests/mcp.test.mjs tests/tool-gateway.test.mjs tests/openai-agent.test.mjs`. Tests use both in-memory transport and a separate test-only stdio process with a disposable shared SQLite database; they check that approval survives process restart. Internal tool exceptions are replaced with a generic error. There is no deployable endpoint, remote authentication or live Foundry integration. The hard-coded identity is a local test fixture, not production authentication; the stdio server fixture is not intended for use outside tests.

The SQLite execution endpoint claims the requested invoice's job specifically. If that job is already running, it returns HTTP 202 and the gateway reports `pending`, rather than declaring completion. A regression test covers an unrelated queued job and a running requested job. The PostgreSQL path has been changed to target the requested job too, with an integration test requiring a disposable PostgreSQL database; until that test runs successfully the PostgreSQL change remains unverified. Neither implementation is a production-ready distributed payment system.

The adapter in `api/openai-agent.mjs` constructs a real `@openai/agents` Agent and a function tool. The only tool requests a simulated operation from an injected local ActionLedger app; it has no direct database access and cannot approve an invoice. SDK `needsApproval: true` pauses that tool. After SDK approval, ActionLedger independently checks the stored invoice status at its simulation endpoint. A blocked or allowed enqueue for an existing invoice is recorded transactionally in SQLite, and completed simulated effects remain idempotent. These events are local mutable database records, not tamper-proof audit logs.

`node --test tests/openai-agent.test.mjs` runs the real SDK runner with its `ScriptedModel` testing double. SDK tracing is disabled and no API, network, model, cloud resources or real payment is used. The tests verify: (1) SDK interruption prevents tool execution; (2) after SDK approval, the ledger still blocks a pending invoice and retains the event after restart; (3) a separate reviewer can approve it, after which simulation completes; and (4) a separate SDK tool-input guardrail can itself block an oversized amount. There is no claim SDK guardrails cannot implement equivalent policy or persistent logging. The added value shown is defense in depth against an SDK approval being treated as sufficient for this separately enforced ledger policy, with a persisted local record. This is one controlled example, not an empirical general superiority benchmark.

The test identity provider is a fixture. Default app mode lacks authentication. The adapter assumes a trusted server-side app instance; `agent-operator` is a fake fixture credential and MUST NOT be used as production authentication. This is not an independently deployed gateway, multi-tenant isolation, tamper-evident storage, or an externally enforceable barrier: a caller with direct DB access can bypass it. The SQLite event covers simulation attempts for existing invoices, not all calls or authorization failures. The PostgreSQL adapter does not yet implement this new event. No OpenAI hosted model has been invoked or validated.

A future live integration requires an explicitly authorized API account, current pricing and spending controls, a real model, authentication and controlled tracing. It must not run automatically as part of CI. The adapter accepts a model so a future explicitly configured SDK model can be supplied, but live wiring and billing have not been tested. Local test calls do not incur provider token charges.
