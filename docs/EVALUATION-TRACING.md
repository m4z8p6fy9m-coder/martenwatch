# Local evaluations and workflow tracing

## Local evaluation is the primary path

`npm run eval:local` runs the local Node test suite for API, structured telemetry, the security and tenant labs, the OpenAI SDK test double, and process/network reliability; it then runs the development and holdout security datasets. It writes a machine-readable report, dataset SHA-256 hashes, suite output and errors to `data/evals/latest/`, which is gitignored. A failed suite sets a nonzero exit status. Security-suite output contains per-category metrics; dataset files and methodology are under `benchmark/`. Loopback network access is needed for local failure simulation. No provider model, API key, cloud export or upload is used; SDK tracing is disabled in its tests.

This evaluation measures synthetic tests and mocked agent behavior. It is not a live-model evaluation, a secret independent holdout, a production security guarantee, or a statistical capacity experiment. The performance and crash recovery timing experiment is a separate `npm run benchmark:performance`; it is not automatically run on every eval. PostgreSQL integration is not included in `eval:local` and requires a separate test database.

The OpenAI Evals platform is being retired: according to [OpenAI's deprecations](https://developers.openai.com/api/docs/deprecations), existing evals became read-only on 31 October 2026 and the Evals dashboard/API are scheduled to shut down on 30 November 2026. OpenAI Datasets may be explored separately where available, but this project does not implement an OpenAI dataset connector, upload or API dependency. JSONL manifests and all evaluation logic remain local; no external dataset schema compatibility is assumed.

## Workflow events and OpenTelemetry

The SQLite app records privacy-minimized workflow events in `workflow_events`. `GET /api/workflows/:id` returns the invoice's policy decision, available agent analysis outcome, blocked/allowed execution gate, reviewer approval decision and completed simulated execution in sequence, when these operations occur. Each row includes a workflow ID (invoice UUID), stage, outcome, timestamp, and the associated request span's trace ID and span ID. In memory, request spans and child spans are visible through `/api/telemetry`. Across separately submitted HTTP requests, trace IDs differ: the durable workflow ID correlates them. This is not a single end-to-end OpenTelemetry trace or W3C trace-context propagation. No prompt, vendor, invoice amount, model output, credentials or reviewer identity is intentionally included in workflow events or spans.

Records survive a SQLite restart. They are operational events, not tamper-evident audit logs. There is no production authentication in default mode; when the test-only identity mode is enabled, workflow reads require `read`. The workflow ID itself is linkable metadata. The local telemetry exporter is bounded and in-memory: it loses spans on restart and does not export to any remote collector. SQLite events can refer to spans that have been evicted or lost. Runtime recovery events, authorization failures before handlers, malformed requests, unknown invoices, and attempts that crash between an operation and the separate event write may not have workflow events. Successful policy and approval events are written in the same transaction as their state change; execution status events are separate writes, so do not treat them as a complete crash-proof audit trail. The endpoint caps output at the first 1000 events. All execution is simulated; no actual payment occurs. The PostgreSQL adapter and standalone external reliability lab are not instrumented by this workflow path. The OpenAI SDK example is not connected to the invoice analysis path; no live-model tracing has been verified.
